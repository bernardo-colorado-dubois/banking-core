FEATURES

What it already does

A minimal core, but with the pieces that matter: access, accounts, operations and a ledger that always balances.

Users and access

JWT login, mandatory password change on first login, profile, admin and operator signup, and user deactivation.

Permissions, never roles

Three fixed roles, each with permissions of the form (action, scope). Authorization never asks for the role.

Account opening

Client signup with their first account, additional accounts for an existing client, and the bank's own accounts.

Atomic operations

Deposit, withdrawal, transfer and reversal, each one a balanced double-entry transaction: either all of its movements are recorded or none are.

Balance and history

An account's movements with the balance each one left, computed in SQL by the account_history view.

Safe concurrency

Row locking with SELECT … FOR UPDATE so two concurrent operations cannot spend the same balance.

ACCOUNTING MODEL

Every account balances with itself

Every account has two sides in the ledger: the main side, which is the balance the holder sees, and the contra, which represents the outside. The main side has a credit nature: a credit increases it and a debit decreases it.

Reversal 2 or 4 movements

CREDIT where the original debited
DEBIT where the original credited

A reversal never edits or deletes the original: it is a new transaction with the same movements and the opposite entry type, so it balances on its own and every account still ends with main + contra = 0. It is rejected if it would leave a main side negative.

  • 1Transaction balance: the sum of debits equals the sum of credits.
  • 2Per-account balance: in each account, main + contra = 0.
  • 3No negative balances: withdrawals and transfers without funds are rejected.
  • 4Positive amounts: the direction is given by the entry type, debit or credit.
  • 5Transfers: source and destination are different accounts.
ARCHITECTURE

The journey of a deposit

The code is organized by business module, user and account, and dependencies point toward the domain. This is what happens on POST /account/{id}/deposit:

1

@authenticated JWT

Validates the token and looks up the user on every request: a deactivation takes effect immediately.

2

routes.py ROUTE

Reads the JSON and checks the required fields. No business rules.

3

SELECT … FOR UPDATE LOCK

Locks the account before computing the balance: two concurrent operations cannot spend the same money.

4

authorize(action, scope) RBAC

Permissions, never roles: DEPOSIT on own, client or bank accounts.

5

Transaction.validate() DOMAIN

Builds the movements and applies the 5 invariants before persisting.

6

COMMIT POSTGRESQL

Transaction and movements in a single commit, which releases the lock.

No float

Decimal in Python and NUMERIC(18,2) in the database. The API returns amounts as text with 2 decimals.

No deadlocks

A transfer always locks both accounts in the same order, by id.

One service per operation

Not one per role: the same AccountFunder serves the client and the admin. The difference is resolved by the account's scope.

ROLES AND PERMISSIONS

A permission is the pair (action, scope)

The scopes are OWN (the authenticated user's accounts), VOSTRO (any client account) and NOSTRO (the bank's accounts). In a transfer the permission is evaluated only on the source account.

GETTING STARTED

Five steps to run it

You need Python, Docker and PostgreSQL 15 or later; the project's container uses PostgreSQL 17.

# 1. Environment variables
cp .env.example .env            # and adjust the values

# 2. Dependencies
python -m venv venv
venv/bin/pip install -r requirements.txt

# 3. Database
docker compose up -d

# 4. Schema, roles, permissions and first admin
venv/bin/python create_admin.py

# 5. Development server at http://localhost:8080
venv/bin/python app.py
create_admin.py is destructive: it drops and recreates every table and the account_history view. Today it is the only way to create the schema, because there are no migrations yet.
